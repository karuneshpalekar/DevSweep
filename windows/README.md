# DevSweep for Windows

The Windows port of DevSweep. See [PLAN.md](PLAN.md) for the goals, the
accuracy traps and the milestones. This folder holds milestones **M0** (the
solution skeleton, CI, and a spike proving the filesystem primitives every
size and every removal rests on) and **M1** (the filesystem layer and safety:
walker v2, the safety guard, quarantine, Restart Manager blockers, the cleaner
and History; see [M1](#m1-filesystem-layer-and-safety)).

Windows 11 (22H2, build 22621) or later, x64.

## Build and test

You need the .NET 10 SDK (`global.json` pins 10.0.100 and rolls forward to
any newer 10.0 feature band).

```powershell
cd windows
dotnet build DevSweep.slnx -c Release
dotnet test tests/DevSweep.Core.Tests -c Release
dotnet test tests/DevSweep.Accuracy -c Release --logger "console;verbosity=detailed"
dotnet publish src/DevSweep.Cli -c Release -r win-x64 -o artifacts/cli   # Native AOT
artifacts\cli\devsweep.exe measure $env:USERPROFILE\.nuget\packages
artifacts\cli\devsweep.exe measure C:\some\folder --json --time-limit 30
artifacts\cli\devsweep.exe measure C:\some\folder --no-streams        # faster, no handle per file
artifacts\cli\devsweep.exe quarantine list                              # size and age of each item
artifacts\cli\devsweep.exe quarantine restore <id>
artifacts\cli\devsweep.exe quarantine empty --older-than 30 --yes
artifacts\cli\devsweep.exe history                                      # where every removed item went
artifacts\cli\devsweep.exe history restore <id>
```

The accuracy suite builds its fixtures (hard links, junctions, compressed and
sparse files, denied folders, paths over 260 characters) under
`%TEMP%\DevSweepFixtures` on a real NTFS volume and removes them afterwards.
It runs as a normal user. The two symbolic-link tests skip themselves when the
account may not create symlinks (no Developer Mode and no privilege); junctions
need no privilege.

CI (`.github/workflows/windows.yml`, `windows-latest`, x64) is the build and
test authority: restore, Release build with warnings as errors, both test
projects (TRX results uploaded as an artifact), the accuracy suite a second
time as a freshly created standard user (`eng/run-as-standard-user.ps1`), a
Native AOT publish of the CLI and a smoke run of `devsweep measure`,
`quarantine` and `history`.

## Layout

```
windows/
  DevSweep.slnx                 solution
  global.json                   .NET 10 SDK
  Directory.Build.props         shared settings: net10.0-windows10.0.22621.0, x64, nullable,
                                warnings as errors, recommended analyzers, code style in build
  Directory.Packages.props      central package versions
  .editorconfig
  src/
    DevSweep.Core/              engine, no UI
      NativeMethods.txt         Win32 APIs generated by CsWin32
      Platform/                 the filesystem layer (below)
        Recycling/              Recycle Bin checks, recycling, $I/$R index and restore
        Quarantine/             same-volume quarantine (move, list, restore, empty)
      Safety/                   SafetyGuard: path rules, protected folders, final-path check
      Cleaning/                 Cleaner, History store, command runner, the Finding/Action model
      Storage/                  atomic file writes, source-generated JSON
    DevSweep.Cli/               devsweep.exe (System.CommandLine, Native AOT, source-generated JSON)
    (DevSweep.App/)             WinUI 3 app: arrives in M4
  tests/
    DevSweep.Core.Tests/        unit tests of pure logic
    DevSweep.Accuracy/          fixture-based accuracy suite (PLAN section 6)
    DevSweep.Fixtures/          builds NTFS edge cases for the suite (also: a Cloud Files sync
                                provider, an exFAT virtual disk, a process holding a file open)
  eng/
    run-as-standard-user.ps1    runs the accuracy suite as a new non-admin user (CI)
```

Engine conventions: small single-purpose types, Win32 only through CsWin32's
generated `PInvoke` (internal to each assembly), metadata-only file access, no
reflection-based serialisation (the Core project is built with
`IsAotCompatible`, so trim and AOT warnings fail the build).

## Accuracy primitives (the M0 spike)

All in `src/DevSweep.Core/Platform`. Each is proved by tests in
`tests/DevSweep.Accuracy` on the CI runner's NTFS volume.

| Primitive | How | Proved by |
|---|---|---|
| **On-disk size** (`FileInspector`) | `FILE_STANDARD_INFO.AllocationSize` from a handle opened with `FILE_READ_ATTRIBUTES` only; for compressed or sparse files `FILE_COMPRESSION_INFO.CompressedFileSize`; for WOF-compressed files (`compact /exe`, CompactOS) `GetCompressedFileSizeW` through the overlay filter | `AllocationSizeTests`: an ordinary file equals its length rounded up to clusters; an NTFS-compressed 4 MiB text file and a 16 MiB sparse file with a 12 MiB hole report less than their length and exactly what `GetCompressedFileSizeW` reports; a 1 TiB sparse file reports almost nothing; a WOF-compressed file reports its compressed size |
| **File identity and hard links** (`FileIdentity`, `HardLinkLedger`) | Volume serial + 128-bit file ID from `GetFileInformationByHandleEx(FileIdInfo)`, handle opened with `FILE_READ_ATTRIBUTES` and `FILE_FLAG_BACKUP_SEMANTICS \| FILE_FLAG_OPEN_REPARSE_POINT`; files with more than one link are counted once per walk; files whose links are not all inside the walk are reported as shared | `HardLinkTests`: all four names of a file share one identity; a folder holding a file and three hard links to it measures as one file; a link from outside makes the bytes "shared", so freeable = 0 |
| **Walker** (`DirectoryWalker`) | `FindFirstFileExW` (`FindExInfoBasic`, `FIND_FIRST_EX_LARGE_FETCH`) on `\\?\` paths, iterative (no recursion limit); every reparse point is recorded and never entered; size = allocation, deduped by file ID; time limit and cancellation return partial counts with `Complete = false` | `WalkerTests`: junctions (and symlinks where creatable) are listed, not followed, and their targets are not counted; a junction loop terminates; measuring a junction measures the link; a file 15 folders deep (path over 300 characters) is found; zero time limit and cancellation give `Partial`; a folder denied to Everyone counts as `AccessDenied` |
| **Cloud placeholders** (`CloudFiles`) | Classified from directory-entry attributes only: `RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN` or `OFFLINE` mean "placeholder" (counted as 0 bytes, never opened); `PINNED`/`UNPINNED` or a cloud reparse tag without those bits mean "synced, local". All handles also use `FILE_FLAG_OPEN_NO_RECALL` | `CloudFilesTests` (unit). Real Cloud Filter fixtures are M1 |
| **Recycle Bin** (`Recycling/RecycleBin`) | Before recycling: no junction or link on the path (`ReparseGuard`), the drive is fixed, the bin is not turned off (policy `NoRecycleFiles`, BitBucket `NukeOnDelete`), the item (larger of logical and on-disk size) fits the limit (policy `RecycleBinSize` or BitBucket `MaxCapacity`). An unknown limit gives `Unknown`, never "can be restored". Recycles with `SHFileOperationW` (`FOF_ALLOWUNDO \| FOF_NO_UI \| FOF_NORECURSEREPARSE`) and checks the item is gone | `RecycleBinTests`: a small file leaves its folder and the bin's item count grows; an item over the limit is "would be permanent" and left alone; a 1 TiB sparse file is never called reversible; recycling a junction removes the link and keeps the target's files; an item reached through a junction is refused |

`WalkResult` carries `Bytes`, `LogicalBytes`, `Files`, `Complete`,
`ReparsePoints`, `SharedLinkBytes`, `CloudPlaceholderCount`, `AccessDenied`,
`Unreadable` and a `SizeConfidence` (`Exact`, `SharedLinks`,
`CloudPlaceholders`, `AccessDenied`, `Partial`; the most serious wins).
`devsweep measure <path> [--json]` prints all of it, laid out for comparison
with Explorer's "Size on disk", `fsutil` and `du -l`.

### Numbers from CI

From the first green run on `windows-latest` (Windows Server, NTFS, 4 KiB
clusters, run as the runner's admin account, no tests skipped):

| Fixture | Logical | DevSweep on-disk | Reference |
|---|---:|---:|---|
| Ordinary file | 100,000 | 102,400 | 25 clusters of 4,096 |
| NTFS-compressed text | 4,194,304 | 524,288 | `GetCompressedFileSizeW` 524,288 |
| Sparse, 12 MiB hole in 16 MiB | 16,777,216 | 4,194,304 | `GetCompressedFileSizeW` 4,194,304 |
| Sparse, 1 TiB, empty | 1,099,511,627,776 | 0 | |
| WOF (`compact /exe:xpress4k`) text | 4,194,304 | 311,296 | `GetCompressedFileSizeW` 311,296 |
| File + 3 hard links (1 MiB) | 4 names | 1,048,576, 1 file, 3 duplicates | `fsutil hardlink list` |
| 2,000 files, time limit 1/4 of a full walk | | 607 files, `Complete = false` | full walk 2,000 files in 46 ms |

Recycle Bin on the runner's C: drive: BitBucket `MaxCapacity` gave a limit
of 10,194,255,872 bytes; a 64 KiB file was recycled and the bin went from 0
to 1 item (`SHQueryRecycleBin`); the 1 TiB sparse file was judged "would be
permanent".

One finding: on Windows 11 / Server the WOF filter hides its reparse point
from `FindFirstFileExW` (the file shows as a plain `Archive` file, tag 0),
and `FILE_STANDARD_INFO.AllocationSize` already reports the compressed
allocation through the filter. The explicit WOF branch in `FileInspector`
stays for systems or modes where the tag is exposed.

### Known gaps (for M1)

- Alternate data streams are not yet counted (`FileStreamInfo` gives each stream's allocation).
- Small files stored inside the MFT report a few bytes of allocation where Explorer shows 0.
- Folders that are reparse points (OneDrive roots, projected file systems, mounted volumes) are not entered at all.
- Paths of 260 characters or more cannot go through the shell's Recycle Bin; they need DevSweep's quarantine (M1).
- The walker opens each file once (metadata only) to read its allocation and ID; M1 should move to
  `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)`, which returns both for a whole folder from one handle.
